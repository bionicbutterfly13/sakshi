# Sakshi 0.4.0 → 0.9.0 — Implementation Journey

A narrative account of how Sakshi grew from a thin metacognitive
runtime into a typed-monitoring substrate, and why each piece earned
its place. Written for someone who wants to understand the *why* of
the codebase, not just its API.

---

## The starting point

Sakshi began with a small, opinionated thesis: a host application
should be able to embed a **Witness** into its agent — a watcher that
observes plan execution, evaluates against expectations, and steers
cognition without doing the cognition itself. The package existed.
The Witness pattern existed. What was missing was the *typed surface*
the Witness needs to do its job well.

There was also a complication. A previous draft plan, generated by a
different agent, had been partially executed against the codebase.
Some of it was real engineering improvement (the six-phase meta-cycle
expansion in `meta/controller.py`). Some of it was research-flavored
import that did not belong in Sakshi (a pair of control-action enum
entries named after Dionysus 3 concepts, and a small emitter module
that propagated those names). The first job was to separate the
signal from the artifact.

---

## The through-line: the Witness pattern

Everything that follows is shaped by one rule, restated whenever a
proposed feature was on the borderline:

> Sakshi observes the host. Sakshi never models the host's mind.

The Witness pattern is not just architectural mood. It is a hard
discipline that tells you what to build and what to defer. A protocol
that lets the host declare its module contract — observe-able, the
Witness watches it. A subsystem that simulates the host's belief
formation — modelling, not Witnessing.

The audit you triggered after Phase B made this explicit, and the
discipline absorbed about a third of the originally proposed roadmap
into a "deferred or dropped" pile with the reasoning preserved in
each phase's CHANGELOG block.

## Phase A — Typed seams (`0.4.0a0`)

### The situation

Anomalies in the existing code were untagged. Goals had a single
status enum but no notion of *what phase of life* they were in. The
metacognitive cycle had no bounded input — long traces grew without
limit. The planner seam was a list of strings. The control action
enum carried two entries that read as though they had been imported
from somewhere else.

### What we built and why

**`AnomalySourceType` enum (`WORLD | COGNITIVE | COMPOUND`).** Without
a lane tag, a meta-cycle that consumes anomaly events sees a single
muddied stream — environment problems and reasoning problems
conflated. Calibration metrics aggregated across that stream lie. The
fix is one enum and a `source` field on every anomaly DTO at
detection. Now downstream code knows which lane an event is on, and
hosts can route world anomalies to world-model corrections and
cognitive anomalies to meta-cycle adjustments without parsing.

**`GoalMode` + `GoalEvent` history.** `GoalStatus` answers "is this
goal still in play?" but not "what is the goal currently doing?" A
goal can be `ACTIVE` whether it is being formulated, dispatched, or
under repair — three very different operational situations. Adding
`GoalMode` as an orthogonal axis (formulating / selected / dispatched
/ monitoring / repairing / deferred / completed) plus a `transitions`
list lets the meta-layer answer the operational question without
guessing. The benefit shows up the first time a host needs to ask
"how many goals are stuck in `MONITORING` for over five cycles?" —
that question becomes a one-line query rather than reconstructing
state from scattered event logs.

**`GoalOperation` taxonomy + `GoalOperationEvent`.** Goal-reasoning
literature names eleven canonical verbs (formulate / select / expand /
commit / dispatch / monitor / evaluate / repair / defer / delegate /
resume). Capturing them as an enum and emitting events makes the
goal lifecycle a queryable timeline rather than a sequence of
disconnected method calls. Hosts that want to study what their agent
is *doing to its goals* over time get a stable surface to subscribe
to.

**`DiscrepancyResolution` DTO.** When the agent finds something
wrong, four steps usually happen: it notices a *symptom*, builds an
*explanation*, formulates a *goal*, and produces a *plan*. Recording
those four steps as a single typed record means a host can audit one
end-to-end resolution chain rather than reconstruct it from events
emitted by four different modules. The same DTO shape works at the
object level (fact-vs-expectation in the world) and the meta level
(phase-output-vs-expectation in cognition); the `level` field makes
which is which explicit.

**`TransparencyLevel` + three tier DTOs.** Hosts surface agent
reasoning to humans at different depths in different contexts: a
status banner, a reasoning chain, a forward-looking projection.
Typing the three tiers separately rather than threading them through
a union lets each consumer subscribe to exactly the depth they need
without unpacking variants.

**`GoalConstraint` (frozen, with `integrity_critical`).** Plans need
bounds: an initial state, safety constraints, goal conditions. The
fourth field, `integrity_critical`, is the contract surface a future
modification guard reads to refuse dropping the constraint. Phase A
introduces the field; Phase F enforces it. The two phases handshake
through this one boolean.

**`TracePruner` protocol with three defaults.** A long-running agent
will accumulate cycle traces without bound. The meta-cycle cannot
reason cleanly over an unbounded trace. Hosts inject a pruner; the
package ships sensible defaults (`LastN`, `SinceAnomaly`,
`WhereExpectationFired`). The benefit is concrete: the meta-cycle's
input stays bounded, and the choice of bound is explicit and
testable.

**`TaskDecomposer` + `Action` DTO.** Plans are stored as `list[str]`
by default. Hosts that want HTN-style decomposition need a seam to
plug a planner in without changing the package. The protocol does
exactly that — and crucially, the package itself never imports a
planner, keeping the dep-light identity intact.

**`ControlActionType.REPLACE_MODULE`.** `SWAP_MODULE` exchanges one
already-registered service for another already-known alternative.
`REPLACE_MODULE` installs a fundamentally different implementation,
typically after a host or operator decision that the previous
service class was unsuitable. The two are operationally different;
typing them separately keeps audit records intelligible.

**Removed: two extraneous control-action entries and their emitter.**
Not part of Sakshi's process. Underlying static-policy-entrenchment
signal returned in Phase B as a properly typed `CanalizationMetrics`.

### Net benefit of Phase A

Every later phase depends on these. Without `AnomalySourceType`,
calibration in Phase B/D would lie. Without `GoalMode`, the
intervention executor in Phase B has no operational context. Without
`integrity_critical`, the guards in Phase F have nothing to grip.
Phase A is the substrate.

## Phase B — Metacognitive substrate (`0.5.0a0`)

### The situation

Sakshi could detect anomalies and raise them, but it could not
quantify how *honest* its own confidence claims were. Every module
was free to attach a `confidence` scalar with no contract. The
existing scalar `consecutive_static_cycles` flagged stuck loops but
did not give the meta-cycle a typed surface to route on.

### What we built and why

**Five-property `ExpectationProfile`.** This is the typed-monitoring
surface. Every module that participates in a cycle declares five
things: latency bound, output schema, confidence range, side-effects
contract, admissible failure modes. Sakshi watches the running module
against the declaration. Three convenience methods
(`confidence_in_band`, `is_declared_failure`, `has_side_effect`)
cover the common checks. The benefit: the day a host wires this up,
every module's contract becomes machine-readable, and violations
produce typed events instead of log strings.

**`CanalizationMetrics` + `CanalizationRisk`.** The single scalar
"consecutive static cycles" promotes to a frozen four-number struct
(depth / dwell time / perturbation resistance / temperature
sensitivity) plus a coarse three-band classifier
(`HEALTHY / DEEPENING / PATHOLOGICAL`). Hosts read the band and
decide whether to widen search precision, swap a module, or
escalate. The benefit over the old scalar: routing decisions can
key on a typed signal that carries enough information to be acted
on, not a raw counter.

**`InterventionExecutor` + `InterventionPermissionPolicy`.** Before
Phase B, control actions could fire without an audit trail. Now
every control action goes through the executor: cooldown check,
permission policy, bounded audit history, optional outcome callback.
Hosts inject their own permission policy when they have richer
safety state. The benefit: typed audit logs of every meta-cycle
intervention, with cooldown protection against thrashing built in.

**`CalibrationTracker`.** The one I am proudest of. Sakshi modules
emit confidence scalars; the tracker watches them against
ground-truth and reports two things: a single `self_trust_score` in
`[0, 1]` (geometric average of how well-calibrated each decile is),
and a list of `CalibrationWarning` records identifying which
confidence bands are miscalibrated. Hosts that see "0.9 confidence
claims are right only 60% of the time" can widen the
`confidence_range` on the offending module's `ExpectationProfile`
rather than blanket-suppress. This consolidated two originally
separate proposals (one called "self-trust assessment", one called
"calibration auditor") into one tracker on one surface — same math,
half the complexity.

**`GoalLineageAuditor`.** Goals do not stay still. Generalize,
specialize, abstract, concretize — long agent runs produce goals
that bear little resemblance to what the host originally posted.
The auditor walks the `metadata["source_goal_id"]` chain and reports
a typed `LineageReport` with depth, widening-step count, transform
chain, and a verdict (`ALIGNED / WARN / DRIFTED`). Hosts route the
report to a pre-INTEND gate or an operator dashboard. Originally
proposed as `IdentityResonanceAuditor`; renamed during the audit to
neutral systems-engineering vocabulary. Same mechanism, more
intelligible name.

**`GoalOutcomeMemory.recent()` / `find_similar()` / `hit_rate()`.**
Existing typed log of goal closures got three retrieval accessors:
recent records, records sharing a predicate name, and the
fraction-achieved scalar. No new module — extending the existing
store rather than adding a parallel "episodic learning" thing was a
deliberate choice from the audit. Hosts that want a learning
strategy on top of these retrievals build it themselves; the package
stays a record log.

### What got audited out

`CognitiveParticle` (Sandved-Smith atoms) — built, then reverted.
Active-inference vocabulary; modelling host beliefs is the host's
job, not Sakshi's. Attention-schema → opacity wiring deferred:
over-engineered for the gap it was meant to close. Both of these
were the audit calling its shot for the first time — and the
pattern recurred in every later phase.

### Net benefit of Phase B

The Witness now has a real substrate. Every event coming out of
Sakshi can be checked against a declared contract. Every confidence
claim can be calibrated against ground-truth. Every intervention
leaves a typed audit trail. Every long-running goal can be checked
against its origin.

## Phase C — Decision-quality upgrades (`0.6.0a0`)

### The situation

The substrate worked, but the meta-cycle still ran on every
iteration regardless of need; goals from the host were always
accepted; plans had no risk vocabulary; failure modes had no axis
to route on; and explanations collapsed to a single best guess
even when two hypotheses were nearly tied.

### What we built and why

**`MetaSchedulingPolicy` + three defaults.** The meta-cycle is not
free. `EveryCyclePolicy` keeps the old behavior; `OnAnomalyPolicy`
runs only when an anomaly fired; `ThrottledByLoadPolicy` reads the
Phase B `CanalizationMetrics` and skips runs when load is
pathological — with a configurable anomaly override so a stuck
agent can still get help. The benefit: hosts that find the meta
layer expensive can throttle it without losing crisis response.

**`DeliberationGate`.** Cost-aware reasoning escalation as a pure
threshold function. Given current confidence, recent failure rate,
and remaining budget, recommend `routine` or `deliberative` path.
Conservative defaults: stay routine unless confidence is below 0.6
*or* failure rate above 0.4 *and* budget is above the floor.
Originally proposed as "S1/S2 arbitration" (Kahneman vocabulary);
renamed during the audit. The math is identical; the name is
closer to what users actually think about.

**`RebelHook`.** Pre-INTEND seam where the meta-layer evaluates an
assigned goal against expectations and returns one of three
verdicts: `ACCEPT`, `REWRITE` (with a substitute goal), `REJECT`
(with a reason). Default `AcceptingRebelHook` is fully
backward-compatible. Production hosts inject a hook that consults
their safety state. The benefit: principled refusal becomes a typed
operation with an audit trail, not an exception buried in a try-
except somewhere.

**`AnticipatoryRiskScorer`.** A three-step pipeline (identify via
host `RiskModel`, aggregate, classify into `RiskBand`) for the EVAL
phase. The host owns the domain-specific risk model; Sakshi owns
the typed pipeline so every plan produces a comparable
`PlanRiskAssessment`. The benefit: comparing risk across plans
becomes a structural operation rather than a bespoke effort per
host.

**`InterventionType` taxonomy.** The `InterventionExecutor` from
Phase B records *what action* fired (mechanism level). It did not
record *what pattern* was being attempted (intent level). One
mechanism can serve many patterns: an `ADJUST_PRECISION` action can
implement `DROP_CONFIDENCE` or `WIDEN_SEARCH` depending on the
precision delta sign. Adding the eight-pattern enum
(`PAUSE_AND_REEVALUATE | DROP_CONFIDENCE | WIDEN_SEARCH | RELAX_GOAL
| FLUSH_MEMORY | TRIGGER_EXPLORATION | SUSPEND_RECOVERY |
ESCALATE_TO_OPERATOR`) and an optional `pattern` field on records
makes intent intelligible in audit trails.

**`TRAPDimension` classifier.** Failure modes have an axis. A
failure of *Reasoning* suggests swapping the reasoning module; a
failure of *Perception* suggests strengthening the perception
pipeline; a failure of *Transparency* suggests asking the host for
more visibility before acting. Tagging each `FailureMode` along the
four-axis taxonomy (Transparency / Reasoning / Adaptation /
Perception) plus the `TRAPRouter` that maps the axis to a
recommended `ControlActionType` gives hosts a typed default routing
they can override per deployment. Deterministic keyword matching
plus an explicit `trap:<axis>` override in description text — no NLP,
no host-callable inference, fully auditable.

**`AnomalyExplainer.explain_distribution(top_k=N)`.** Where the
single-best `explain` collapses to the most-shifted key,
`explain_distribution` returns up to `top_k` competing hypotheses
ranked by confidence. The benefit: when the top-1 confidence does
not exceed the runner-up by a comfortable margin, the host should
defer or gather more evidence rather than commit to a high-impact
intervention. The distribution makes that decision explicit.

### What got audited out

`OptimalityMeasure` protocol — `GoalSelector` already takes a
swappable `criteria` object; the new protocol would have been a
parallel name for an existing seam. `EmergenceBound` (Type I-IV) —
multi-agent territory; belongs in a host adapter.

### Net benefit of Phase C

The agent now has typed primitives for *when to think harder*, *how
to respond to assigned goals*, *how to assess plan risk*, *what
kind of intervention to label*, *how to route different failure
modes*, and *how to hedge across competing diagnoses*. The
machinery exists for hosts that want it.

## Phase D — Trust calibration & uncertainty (`0.7.0a0`)

### The situation

Sakshi reported confidence as a single scalar. That scalar
collapses two distinct questions an operator usually needs to
answer separately: *how reliable was the capability that produced
this output*, and *how trustworthy is the signal pipeline itself*.
A single integrity breach can decay trust faster than competence
drift; conflating them obscures which axis is actually failing.

### What we built and why

**`TrustBifurcation`.** Two-axis self-trust DTO splitting
`competence_confidence` from `integrity_confidence`. The
`aggregate` property combines them via geometric mean — a weakness
on either axis penalizes the score, which is the correct behavior:
a competent capability with a compromised pipeline is no more
trustworthy than an honest pipeline emitting incompetent output.

**`UncertaintyType` enum.** Three modes (`PROBABILITY |
AMBIGUITY | IGNORANCE`). Lets a host ask whether a confidence value
reflects a single modeled hypothesis, a hedge across competing
hypotheses, or a no-model placeholder. Each mode usually warrants a
different downstream response; without the typing, the host has to
guess.

**`TrustReport`.** Composite host-facing DTO. Bundles a
`TrustBifurcation`, an `UncertaintyType`, the labels of competing
hypotheses (when applicable), a calibration status, a coarse
trajectory band, and a recommendation string. The surface humans
see. The benefit: the report has all the typed primitives an
operator needs to make a routing decision in one round-trippable
DTO.

**`ConfusionWeighter`.** Cost-matrix decision helper. Real hosts
have asymmetric costs — a missed safety-critical fault costs more
than a missed cosmetic one. Naive arg-max ignores that. The
weighter takes a probability vector and a `{predicted: {true:
cost}}` matrix and picks the class minimizing expected cost,
returning a `ConfusionDecision` that records both the cost-weighted
choice *and* the naive arg-max baseline. The audit benefit is
real: a reviewer can see exactly what the asymmetric cost structure
changed.

### What got audited out

`MetaConfidence` (Gaussian-over-confidence), `TrustTrajectory`
parametric curve, `MiscalibrationPattern` detector,
`CoherenceWarning` emergence-anomaly detector. All proposed; all
deferred. The Phase B `CalibrationTracker` already produces
per-decile warnings; multi-agent coherence belongs in a host
adapter.

### Net benefit of Phase D

Sakshi now has the primitives to be honest about its own
confidence on the right axes, and to act on asymmetric error costs
when the host cares about them. The Witness can report what it
saw without flattening the structure.

## Phase E — Motivation surface (`0.8.0a0`)

### The situation

Every later observation about an agent's behavior eventually has to
answer: *why did the agent want to do that?* A goal arrived from
the host's planner, but the planner was driven by some intrinsic
motivation — achievement, novelty, power, surprise — and that
motivation has consequences for safety and explainability. Sakshi
needed a typed surface to observe motivation without modelling it.

### What we built and why

**`MotivationType` enum.** Coarse taxonomy of motivation sources
(`ACHIEVEMENT | AFFILIATION | POWER | NOVELTY | COMPETENCE |
SURPRISE | EXTRINSIC | UNCLASSIFIED`). The host tags every
intrinsic goal with the type that produced it. Sakshi never
generates motivation; it just observes the host's record. The
benefit: motivation diversity becomes inspectable without the host
reverse-engineering it from goal predicates.

**`MotivationEvent`.** Immutable record per activation. Includes
rejections — the auditor records every motivation impulse, even
the ones that got refused by the envelope.

**`CreativityEnvelope` + `evaluate_envelope()`.** Bringsjord's
argument is that creative + autonomous machines are intrinsically
untrustworthy *unless explicitly constrained*. The envelope is the
constraint surface: allowed predicates, forbidden attributes, max
novelty score, forbidden motivation types. `evaluate_envelope()`
is a pure function that returns an `EnvelopeVerdict`. Goals
outside the envelope are *rejected with reason* and the rejection
flows through the auditor — operators can later query the system
about rejected impulses, which closes the interrogability loop.

**`GoalRelevanceFilter`.** Host-declared value-tag taxonomy.
Optional `require_value_tag` strict mode. Filters motivated goals
against organizational value tags so an agent in a deployment
context cannot pursue a goal that does not trace back to a
declared value.

**`ComputationalMotivationMetrics`.** Frozen four-scalar summary
(`diversity_score | stability_score | risk_assessment |
communication_cost`), all bounded to `[0, 1]`. Hosts route on
them with simple thresholds. Diversity surfaces single-drive
domination; stability surfaces oscillation between accepting and
rejecting impulses; risk surfaces creep toward power and surprise
motivation; communication cost approximates how much
human-facing narrative the system is producing.

**`MotivationAuditor`.** Bounded ring-buffer audit log. Records,
filters by type, reports acceptance rate, and produces the
metrics view on demand. Never decides — that is the host's job,
gated by the envelope and the relevance filter.

### What got audited out

The full CLARION-style two-level motivation subsystem (implicit
drives feeding explicit goals) and the entropy-based curiosity
scorer. Both model the host's mind, which is outside Sakshi's
scope. Hosts that want them implement them internally and emit
`MotivationEvent` records into the auditor. The
`NarrativeMotivationJustifier` and `MotivationDriftDetector` were
deferred — the metrics view already surfaces drift via
`diversity_score` and `stability_score`.

### Net benefit of Phase E

Sakshi can now observe a host's intrinsic-motivation system
without becoming one. The envelope gates creativity to a host-
declared safe region; rejections are typed and audited; metrics
surface drift early. The Witness pattern is preserved: Sakshi
watches motivation; the host generates it.

## Phase F — Defensive guards (`0.9.0a0`)

### The situation

Two failure modes Hutter's universal-AI work calls out had no
defenses in Sakshi. *Wireheading*: an agent silently records "goal
achieved" without the world having moved. *Self-modification
drift*: a self-modifying agent quietly relaxes a safety-critical
constraint. Phase A introduced the `integrity_critical` flag on
`GoalConstraint`; Phase F finally makes it enforceable.

### What we built and why

**`RewardIntegrityGuard` + `EvidenceRequiringRewardIntegrityGuard`.**
A goal-achievement claim only counts if the host can show
*exogenous evidence* — sensor readings, completed tool calls,
observed state-change events — that the world actually changed.
The default guard requires at least `min_evidence` keys; hosts
wanting richer logic (signature verification, redundant
confirmations, time-window checks) supply their own implementation
of the protocol. The benefit: silent goal-claim counterfeiting
becomes harder to commit and easier to audit.

**`ModificationIntegrityGuard` + `IntegrityCriticalModificationGuard`.**
When a self-modifying agent wants to drop or relax a
`GoalConstraint`, the guard refuses if the constraint is flagged
`integrity_critical=True`. Specifically denies (a) demoting a
critical constraint to non-critical and (b) dropping any safety
constraint from a critical constraint's `safety_constraints` list.
This is the Phase A → Phase F handshake: the flag introduced four
phases ago finally enforces what it was promising.

**`GuardVerdict` + `GuardDecision` + `GuardAuditRecord`.** Shared
typed result shape across both guards, plus a frozen audit
wrapper. The benefit: hosts get one unified audit log across both
guard types, streamable through their event bus.

**`KnowledgeRewardBalance` enum.** `KNOWLEDGE | REWARD | HYBRID`
preference plus two predicate helpers. Hosts use the predicates
when deciding whether to suppress a curiosity-motivated goal
because the budget is exhausted and the agent should be
exploiting. Small but real.

### What got audited out

`EpistemicState` (multi-agent theory-of-mind seam) deferred.
Sakshi is single-agent by default; multi-agent belief tracking
belongs in a host adapter.

### Net benefit of Phase F

The two failure modes a generally-capable autonomous system has to
defend against now have typed validation seams. The defaults are
sensible; the protocols are pluggable; the audit trail is
unified.

## Phase G — Principles, provenance, version cut (`0.9.0`)

### The situation

After six phases of code, the *durable* design artifacts had drifted
behind the implementation. The principles document still reflected
the 0.3.0 surface; the inspirations document did not credit
half the chapters that shaped the typed surface; the version was
still alpha-tagged.

### What we did and why

**Five new principles.** Anomaly lane integrity (every anomaly
tagged at detection; calibration per lane). Two-axis self-trust
(competence and integrity reported separately). Goal-creativity
envelope (creative outputs validated against an explicit
host-declared envelope). Goal interrogability (every goal
traceable to its source). Defensive guard discipline (achievement
claims pass through `RewardIntegrityGuard`; `integrity_critical`
constraints protected by `ModificationIntegrityGuard`).

These are not new code — they are the rules a future contributor
needs to know to keep the codebase coherent. The benefit is
durability: the principles outlast the specific implementation
choices that gave rise to them.

**Provenance updates.** CLARION (Sun) added for the motivation
taxonomy. Goal Lifecycle Networks (Roberts, NRL) added for
`GoalMode` and the `GoalOperation` taxonomy. New section
attributing Phase D / E / F shape and naming to specific chapters
in *Foundations of Trusted Autonomy* (Abbass / Scholz / Reid eds.,
2018, Springer Open) — Devitt for trust bifurcation, Smithson for
uncertainty taxonomy, Hart et al. for communicative-cue framing,
Scholz for confusion-objective error shaping, Merrick for the
motivation taxonomy, Bringsjord for the creativity-trust caveat,
Hutter for the defensive failure-mode taxonomy. The benefit is
honest credit and discoverability — readers who want to dig into
the source for a specific Sakshi primitive know exactly where to
go.

**Version cut to `0.9.0`.** Six implementation phases plus the
principles sweep stabilized the public surface enough to leave
alpha tagging behind.

---

## What the discipline added up to

By the time `0.9.0` cut, the audit had absorbed seventeen
originally-proposed items into a "deferred or dropped" pile, every
one of them documented with reasoning in a CHANGELOG block. That
discipline is the most important thing the journey produced. The
typed primitives are valuable; the discipline that decided which
typed primitives to *not* build is what kept the package coherent.

The Witness pattern survived contact with the roadmap because
every borderline proposal got the same question: *does this
observe the host, or does it model the host's mind?* When the
answer was *observe*, the feature shipped. When the answer was
*model*, the feature got deferred to the host adapter or the
host's own code, with the reasoning preserved so a future
maintainer would not have to re-litigate it.

## The current shape

Sakshi at `0.9.0` is what it was meant to be at the start: a
small, deterministic, dep-light, seam-first runtime that lets a
host embed a Witness into its agent. The Witness now has a real
typed surface — module contracts, anomaly lanes, goal lifecycles,
trust bifurcation, motivation envelopes, defensive guards. None
of it imports a host runtime. None of it requires a heavy ML
dependency. None of it pretends to be more than the package was
honestly able to deliver.

The package is ready for hosts to build against. The principles
document tells future contributors how to keep it that way.
